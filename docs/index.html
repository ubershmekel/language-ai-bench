Does your programming language change how well AI codes?

Same task, same model, same agent, fresh context every run. Only the language changes.

Results

Each language attempted two hard refactors, 24 times each. Python appears twice because one version adds type annotations and a type checker, holding everything else fixed. An agent step is one model action: read a file, run a command, apply an edit.

The main finding

The two hard tasks disagree about which language wins

Pooling these produces an average that describes neither task. This is why the project reports per task family and never as one score.

  • circuit-breaker Go 7/8 > TypeScript 6/8 > JavaScript 4/8 > Python (typed) 3/8 > Python 2/8
  • money-rollup Python 8/8 > Python (typed) 8/8 > Go 6/8 > TypeScript 6/8 > JavaScript 5/8

What the numbers show

The task decides the winner

One refactor turns on exact decimal arithmetic, where Python has a library that does it correctly out of the box. The other turns on covering every branch of a state machine, where a compiler that lists the branches you missed is worth more. Nothing about the model or the agent changed between them.

Adding types to Python changed little

The cleanest comparison holds the language fixed: identical Python, differing only by annotations and a mypy --strict step that must pass before the tests run. The gap in pass rate was +0.042 (95% CI -0.125 to 0.208), an interval spanning zero. At this sample size no effect on correctness is detectable, which is a legitimate answer rather than a failed experiment.

Checking still costs work

JavaScript needed fewer agent steps than TypeScript, typed Python, and Go; plain Python needed fewer than Go. Those intervals do clear zero. The price in effort shows up reliably even where a benefit to correctness does not.

What would change this

Two refactors that discriminate is not enough to break the tie between them; a third would help more than more repeats of these. Eight attempts per cell is thin, so the reversal is stark but the exact ordering inside either task is not worth leaning on. A language here is a bundle including its toolchain and ecosystem, so none of this is a claim about syntax.

Method and tasks

money-rollup

A command-line reporting tool has to stop doing money math in floating point. It switches to exact arithmetic, converts currencies along the shortest rate path and rejects ambiguous ones, totals every parent account, rounds half-to-even per entry, and rejects about thirty kinds of malformed input.

circuit-breaker

A simulator has to track one breaker per target through closed, open, and recovering, opening after enough consecutive failures, recovering only once a cooldown has elapsed, limiting trial calls while recovering, and treating an unlisted status code as neither success nor failure. Its starting code fails nine of twelve hidden checks in every language.

Why these two

Earlier rounds were too easy: everything passed, which pins every difference at zero and answers nothing. These fail often enough to compare. They were also chosen to stress different things, which is how the reversal above became visible at all.

Calibration

Before any paid run: reference solutions pass every check, the four untouched starters fail the identical eight checks, and four seeded sabotages are caught with identical failure sets in every language. Instructions are byte-identical across languages and the hidden expectations are not readable from the workspace.

Uncertainty

Intervals are 95% percentile intervals from a fixed-seed 20,000-resample paired bootstrap over matched attempt blocks. The number of runs was fixed at 120 before the first paid call and no interim look influenced whether to continue.
