Does your programming language change how well AI codes?

Same task, same model, same agent, fresh context every run. Only the language changes.

Results

Each language attempted three refactors, 24 times each. Python appears twice because one version adds type annotations and a type checker, holding everything else fixed. An agent step is one model action: read a file, run a command, apply an edit.

The main finding

The two hard tasks still disagree, and the order is not stable

Pooling these produces an average that describes neither task. This is why the project reports per task family and never as one score. The third task added this round was too easy to rank anything and is not shown.

  • circuit-breaker JavaScript 6/8 > Go 4/8 > Python (typed) 4/8 > Python 2/8 > TypeScript 2/8
  • money-rollup Python (typed) 7/8 > Python 6/8 > TypeScript 6/8 > JavaScript 5/8 > Go 4/8

What the numbers show

The task decides the winner

One refactor turns on exact decimal arithmetic, where Python has a library that does it correctly out of the box. The other turns on covering every branch of a state machine, where a compiler that lists the branches you missed is worth more. Nothing about the model or the agent changed between them.

Adding types to Python changed little

The cleanest comparison holds the language fixed: identical Python, differing only by annotations and a mypy --strict step that must pass before the tests run. The gap in pass rate was +0.125 (95% CI -0.125 to 0.375), an interval spanning zero, the same answer this pair gave last round. At this sample size no effect on correctness is detectable, which is a legitimate answer rather than a failed experiment.

Checking still costs work

JavaScript needed fewer agent steps than TypeScript, typed Python, and Go; plain Python needed fewer than Go. Those intervals do clear zero. The price in effort shows up reliably even where a benefit to correctness does not.

Eight attempts is thin, and here is the proof

Both hard tasks were rerun this round with nothing changed but the random seed. TypeScript went from 6 of 8 to 2 of 8 on the state machine, Go from 7 of 8 to 4 of 8. The disagreement between the two tasks survives; the exact order inside either one does not, and no reading that leans on it is safe. A language here is a bundle including its toolchain and ecosystem, so none of this is a claim about syntax.

Not sure what a score like 2 out of 8 means? How a run is scored walks through one real failure step by step. Every paired contrast and the per-case failure breakdown are in the written report.

Method and tasks

money-rollup

A command-line reporting tool has to stop doing money math in floating point. It switches to exact arithmetic, converts currencies along the shortest rate path and rejects ambiguous ones, totals every parent account, rounds half-to-even per entry, and rejects about thirty kinds of malformed input.

circuit-breaker

A simulator has to track one breaker per target through closed, open, and recovering, opening after enough consecutive failures, recovering only once a cooldown has elapsed, limiting trial calls while recovering, and treating an unlisted status code as neither success nor failure. Its starting code fails nine of twelve hidden checks in every language.

text-redact

A redaction tool has to count every offset and length in Unicode code points rather than in whatever unit its language indexes strings by, then merge overlapping and touching spans, drop short ones before merging, and reject a wide set of malformed input. It was added this round to break the tie between the other two, and it failed to: 39 of 40 attempts passed, and not one tripped the code point trap. The instruction stated the rule too loudly. That is a fix to the task, not to the result.

Why these tasks

Earlier rounds were too easy: everything passed, which pins every difference at zero and answers nothing. The first two fail often enough to compare, and they were chosen to stress different things, which is how the disagreement above became visible at all. The third shows that a task can pass every free calibration check and still be too easy.

Calibration

Before any paid run: reference solutions pass every check, the five untouched starters fail the identical checks, and four seeded sabotages are caught with identical failure sets in every language. Instructions are byte-identical across languages and the hidden expectations are not readable from the workspace. A green gate proves the scoring is fair, not that the task is hard enough to tell the languages apart.

Uncertainty

Intervals are 95% percentile intervals from a fixed-seed 20,000-resample paired bootstrap over matched attempt blocks. The number of runs was fixed at 120 before the first paid call and no interim look influenced whether to continue.
