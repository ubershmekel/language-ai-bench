Does your programming language change how well AI codes?

Same task, same model, same agent, fresh context every run. Only the language changes. Across 24 runs per arm on two hard refactors, the answer flipped with the task: Python passed every attempt on one and two of eight on the other, where Go led instead. A single ranking across tasks would have hidden that.

The main finding

The two hard tasks rank the arms in opposite orders

Pooling these produces an average that describes neither task. This is why the project reports per task family and never as one score.

  • circuit-breaker Go 7/8 > TypeScript 6/8 > JavaScript 4/8 > Python (typed) 3/8 > Python 2/8
  • money-rollup Python 8/8 > Python (typed) 8/8 > Go 6/8 > TypeScript 6/8 > JavaScript 5/8

What the data says

What the numbers show

The task decides the winner

On money-rollup, which turns on exact decimal arithmetic, Python passed all eight attempts and JavaScript five. On circuit-breaker, which turns on covering every case of a state machine, Python passed two of eight and Go seven. Same model, same agent, same day. The ranking is a property of the task at least as much as of the language.

Adding types to Python changed little

The cleanest comparison here holds the language fixed: the same Python, differing only by annotations and a blocking mypy --strict step. The difference in pass rate was +0.042 (95% CI -0.125 to 0.208), an interval that includes zero. At this sample size the study does not detect an effect on correctness, which is a result and not a failed experiment.

Type feedback still costs work

JavaScript needed fewer agent steps than TypeScript, typed Python, and Go, and Python fewer than Go, all with intervals clear of zero. Checking has a price in effort that shows up reliably even where its benefit to correctness does not.

What would change this

Three task families, eight attempts per cell, one model snapshot, one bash-only agent scaffold. The language is a bundle that includes its toolchain, file layout, and ecosystem, so none of this is a claim about syntax. Eight attempts is thin: the direction of the reversal is stark, but the ordering within either task is not something to lean on.

Every paired contrast, the per-case failure breakdown, and the weaker-model cohort are in the written report, with the earlier v0.7 cohort preserved.

Extra notes

Method and task

The task

A four-file command-line reporting tool has to stop doing money math in floating point. The agent switches to exact arithmetic, converts currencies along the shortest rate path and rejects ambiguous ones, totals every parent account, rounds half-to-even per entry, and rejects about thirty kinds of malformed input. The starter code fails eight of the twelve hidden checks in every language.

Why this task

Earlier rounds were too easy. Every language passed everything, which pins each difference at exactly zero and answers nothing. This one fails often enough to compare, which is the whole point of replacing it.

Calibration

Before any paid run: reference solutions pass every check, the four untouched starters fail the identical eight checks, and four seeded sabotages are caught with identical failure sets in every language. Instructions are byte-identical across languages and the hidden expectations are not readable from the workspace.

Uncertainty

Intervals are 95% percentile intervals from a fixed-seed 20,000-resample paired bootstrap over matched attempt blocks. The strong rung was collected in two batches of 48; the second ran because the first left Python versus Go touching zero, so that continuation was outcome-dependent and the report says so.
